## G2: `Handshaker.remotePeer` race

**Defect:**
- `Handshaker.Name()` returns `h.remotePeer.String()`. The Container's close callback calls it to log the endpoint, on another goroutine.
- `handshakeMsg` replaces `h.remotePeer` with the identity the peer declared, on the remote endpoint's message goroutine.
- `dndm.Peer` is an interface (two words), so this is a real torn-read risk, not only a detector report.
- Both lines date from the pin. The alias case (a connection closed while its handshake runs) makes them meet.

**Fix:**
- A `peerMu sync.RWMutex` guards `remotePeer`.
- Every read goes through `h.peer()`; the one write in `handshakeMsg` takes the lock.
- The tie-break `AddConn` uses the local `peer` value.
- The `endpoint/mesh` API is unchanged (`go doc -all` diff empty).

**Test:** `TestHandshaker_NameDuringHandshake` (`name_race_test.go`).
- It opens a pair and reads `Name()` on both handshakers in a loop for the whole handshake. Then it checks that each side names the other by its declared identity.
- It needs `-race` to fail, and the gates run with `-race`.

## G1: alias subtest interest lost to the tie-break loser

**Cause**, confirmed by the mutant below and by the after-run:
- When two nodes dial each other under alias names, both connections are ready for a moment (close-reconnect.md §3.1 residual). B registers its interest on each connection when that connection becomes ready.
- The subtest waited for the first interest notification on A and then sent once. That notification can come from the connection that loses the tie-break.
- When the loser closes, its remote interest goes with it. If the survivor's interest is not linked yet, `Send` returns `ErrNoInterest`.
- So the interest is not lost for good; it arrives over the survivor shortly after.

**Fix (test):**
- The subtest now retries `Send` while it returns `ErrNoInterest`, for up to 5 s. `FanOutIntent.Send` returns `ErrNoInterest` only when no endpoint had an interest, so nothing was sent and a retry cannot duplicate.
- The subtest still checks that the message arrives exactly once.
- Product behaviour is unchanged. I recorded it next to the duplicate window in close-reconnect.md §3.1: while the loser's link goes, `Send` can briefly report no interest. DND-022's session ids remove both.

## Proposed mb learnings

- 2026-11-09 [go] [medium] A field that a lifecycle callback reads (a name for logs) and a protocol handler rewrites (the declared peer identity) needs a lock even when it "only logs". An interface value is two words, and the race detector flags it as soon as a close and a handshake overlap (dndm DND-008 G2).
- 2026-11-09 [testing] [medium] In a test that sends once after the first "interest" notification, connection churn can produce a notification from a link that is about to close. Retry while the send reports "no receiver", which sends nothing, and still assert exactly-once delivery. Then show with a mutant that the retry does not hide a real loss (dndm DND-008 G1).
